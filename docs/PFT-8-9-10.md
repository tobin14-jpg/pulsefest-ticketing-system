Registration and profile updates reject role fields. Legacy users with no stored role act as attendees. Role claims supplied in a JWT do not grant access; the middleware reads the database user on every protected request. Organisers manage all events in this academic prototype; there is no additional ownership permission layer. Ordinary authenticated booking/browsing remains available to both roles.

## API additions

All use the existing bearer-token authentication, followed by organiser middleware.

| Method | Path | Request / result |
| --- | --- | --- |
| GET | `/api/events/manage` | All events with capacity, reserved and remaining counts |
| POST | `/api/events` | Name, optional description, future ISO UTC date/time, location, numeric price and integer capacity; returns 201 after save |
| PATCH | `/api/events/:id` | Exactly `{ "capacity": 20 }`; returns updated event |

Create accepts a real UTC ISO timestamp such as `2099-12-10T10:00:00.000Z`; the UI converts its local date/time input. Impossible dates, past dates, missing/invalid fields, extra/internal fields, negative prices and prices with more than two decimal places are rejected. Price and capacity must be JSON numbers. `createdBy`, `reservedTickets` and timestamps cannot be supplied by clients.

Authentication errors return 401, organiser denial 403, invalid input 400, missing events 404, reductions below reserved tickets 409 and storage failures a generic 503. Malformed JSON gets a useful 400 response without an Express stack trace.

The capacity update includes `reservedTickets <= newCapacity` in the MongoDB update predicate. It does not read then write capacity in separate unguarded operations. A booking transaction and a capacity reduction contend on the same document, ensuring the final capacity is never less than persisted reservations.
